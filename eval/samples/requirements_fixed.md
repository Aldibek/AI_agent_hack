### Глоссарий

| Термин | Определение |
| :--- | :--- |
| Порог | Сумма в тенге, заданная клиентом для карты на календарный месяц. Других названий (лимит, бюджет) в документе нет. |
| Расходы месяца | Сумма проведённых покупок по карте за календарный месяц за вычетом возвратов по этим покупкам. |
| Проведённая покупка | Покупка, по которой процессинг передал событие `POSTED` (клиринг выполнен). Авторизация без клиринга не учитывается. |
| Дата совершения | Дата и время авторизации покупки по времени Asia/Almaty (UTC+5). |
| Календарный месяц | Период с 00:00:00 первого числа до 23:59:59 последнего числа месяца по времени Asia/Almaty (UTC+5). |
| Сервис расходов | Компонент, который учитывает расходы месяца и решает, отправлять ли push. |
| Сервис push | Компонент, который доставляет push на устройства клиента. |

### Цели
Клиент узнаёт о достижении порога расходов не позднее чем через 60 секунд после проведения покупки, на которой порог достигнут
(измеряется требованием НФТ-1).

### Архитектура решения
Мобильное приложение → AlertsController → хранилище настроек. Карточный процессинг → сервис расходов → сервис push.
Сервис расходов читает порог и признак включения из хранилища настроек.

### Дизайн процесса UI
Путь: Карты → карта → Расходы → Уведомления. Экран получает данные методом `GET /alerts/settings` (часть B) и показывает:
переключатель «Уведомлять о пороге», поле «Порог, ₸», строку «Расходы за {месяц}: {сумма} ₸» и кнопку «Сохранить».
Кнопка сохраняет данные методом `PUT /alerts/settings`. При ответе 400 под полем «Порог, ₸» показывается текст из поля
`message` ответа. При ответах 401, 404 и 500 показывается экран ошибки «Не удалось загрузить настройки, повторите позже».

### Требования к изменениям

#### BPMN схема процесса
1. Процессинг передаёт событие `POSTED` или `REFUND`.
2. Сервис расходов проверяет, не обработано ли событие ранее (по `operationId`).
3. Сервис расходов пересчитывает расходы месяца по дате совершения покупки.
4. Если уведомления по карте включены, расходы перешли от суммы ниже порога к сумме не ниже порога и push в этом месяце
   ещё не отправлялся — сервис расходов передаёт push в сервис push.
5. Завершение.

#### Функциональные требования
* **Ф-1** (Must). Держатель активной карты в валюте KZT задаёт порог — целое число тенге от 1 000 до 1 000 000 включительно —
  и включает или выключает уведомление. Для новой карты уведомление выключено, порог не задан.
* **Ф-2** (Must). Покупка относится к календарному месяцу по дате совершения. В расходы месяца входят проведённые покупки
  в торговых точках и в интернете на сумму, списанную в тенге. Переводы, снятие наличных, комиссии банка и пополнения
  в расходы не входят.
* **Ф-3** (Must). Возврат уменьшает расходы месяца, к которому относится исходная покупка, даже если возврат пришёл позже.
  Возврат не отменяет уже отправленный push и сам push не вызывает.
* **Ф-4** (Must). Push отправляется только при обработке проведённой покупки, после которой расходы месяца впервые
  в этом месяце стали не ниже порога. По карте отправляется не больше одного push за календарный месяц, в том числе
  при изменении порога после отправки.
* **Ф-5** (Must). Изменение порога или переключателя не меняет расходы месяца и само по себе push не вызывает.
  Если push в текущем месяце ещё не отправлялся, новый порог применяется к следующей проведённой покупке.
* **Ф-6** (Must). Расходы месяца учитываются и при выключенном уведомлении; при выключенном уведомлении push не отправляется.
* **Ф-7** (Should). Если покупка проведена после окончания месяца, в котором она совершена, она увеличивает расходы
  прошлого месяца, а push за прошлый месяц не отправляется.

### Sequence Diagram
1. Процессинг → сервис расходов: событие `POSTED` или `REFUND` с полями `operationId`, `cardToken`, `amountTiyn`,
   `transactionDateTime` (время Asia/Almaty), `operationType`; для возврата — `originalOperationId`.
2. Сервис расходов → хранилище настроек: получить `limitKzt` и `enabled` карты.
3. Сервис расходов → сервис push: `cardToken`, последние четыре цифры карты, `limitKzt`, расходы месяца в тенге.
   Текст push: «Расходы по карте •• {последние 4 цифры} за {месяц} достигли {расходы} ₸ при пороге {порог} ₸».
4. Сервис push → сервис расходов: подтверждение приёма; после него сервис расходов сохраняет время отправки push.

### Нефункциональные требования
* **НФТ-1** (Must). 95% push передаются в сервис push не позднее 60 секунд после получения события `POSTED`, 99% — не позднее
  120 секунд; измеряется по журналу сервиса расходов за сутки.
* **НФТ-2** (Must). Сервис расходов обрабатывает до 300 событий в секунду в пике без роста задержки сверх НФТ-1.
* **НФТ-3** (Must). Доступность методов части B — 99,5% в месяц.
* **НФТ-4** (Must). Если сервис push не подтвердил приём, сервис расходов повторяет передачу 3 раза с интервалом 60 секунд;
  после трёх неудач push за этот месяц считается неотправленным, событие пишется в журнал ошибок, следующая проведённая
  покупка в этом месяце снова может вызвать push.
* **НФТ-5** (Must). Метрики: задержка от события до передачи push, число ошибок сервиса push, число повторных событий;
  оповещение дежурного при доле ошибок выше 1% за 5 минут.

### Требования к данным
* **Д-1.** Настройки карты: `card_token` (токен карты, не номер карты), `limit_kzt` (целое, тенге), `enabled` (логический),
  `updated_at` (время Asia/Almaty).
* **Д-2.** Расходы месяца: `card_token`, `month` (ГГГГ-ММ по дате совершения), `spent_tiyn` (целое, тиыны),
  `push_sent_at` (время отправки push, пусто, если push не отправлялся).
* **Д-3.** Обработанные события: `operation_id` (уникальный), `card_token`, `amount_tiyn`, `transaction_datetime`,
  `operation_type` (`POSTED` / `REFUND`), `original_operation_id` для возврата.
* **Д-4.** Сравнение с порогом выполняется в тиынах: `spent_tiyn` ≥ `limit_kzt` × 100.
* **Д-5.** Данные хранятся 13 месяцев, затем удаляются.

### Требования к интеграции
* **И-1.** Приложение читает и сохраняет настройки методами части B.
* **И-2.** Событие с уже обработанным `operationId` не меняет расходы месяца и не вызывает push.
* **И-3.** Если возврат пришёл раньше исходной покупки, сервис расходов хранит его 7 дней и учитывает, когда придёт покупка;
  если покупка не пришла за 7 дней, возврат пишется в журнал ошибок.

### Требования к безопасности
* **ИБ-1.** В API, событиях и журналах используется только токен карты; номер карты не передаётся и не записывается.
* **ИБ-2.** Push и экран приложения показывают только последние четыре цифры карты.
* **ИБ-3.** Методы части B доступны только владельцу карты по сессии мобильного банка; для чужой и для несуществующей
  карты возвращается 404, чтобы не раскрывать существование карты.

### Требования к тестированию

#### Тестирование требований
Ответственный — тестировщик команды карт. Требования проверены на тестируемость 27.11.2026; каждое требование Ф-1 – Ф-7,
НФТ-1 – НФТ-5 и ИБ-1 – ИБ-3 покрыто критериями приёмки или проверкой метрик.

### Критерии приемки

| № | Исходные условия | Действие | Ожидаемый результат |
| :--- | :--- | :--- | :--- |
| КП-1 | Уведомление включено, порог 50 000 ₸, расходы месяца 48 500 ₸, push в месяце не отправлялся | Провести покупку на 1 500 ₸ | Расходы 50 000 ₸, отправлен один push |
| КП-2 | Покупка совершена 31 января в 23:58 по Алматы на 4 000 ₸ | Процессинг проводит её 1 февраля в 00:03 | Январские расходы выросли на 4 000 ₸, февральские не изменились, push за январь не отправлен |
| КП-3 | Уведомление включено, порог 20 000 ₸, расходы 19 900 ₸ | Клиент переводит 500 ₸ | Расходы 19 900 ₸, push не отправлен |
| КП-4 | Push в марте уже отправлен при пороге 50 000 ₸ | Клиент меняет порог на 80 000 ₸, затем проведена покупка, после которой расходы 85 000 ₸ | Второй push в марте не отправлен |

| КП-6 | Событие `POSTED` с `operationId` = 777 уже обработано | Процессинг повторно передаёт событие 777 | Расходы не изменились, push не отправлен |
| КП-7 | Покупка на 6 000 ₸ проведена в январе | В феврале приходит возврат по ней на 6 000 ₸ | Январские расходы уменьшились на 6 000 ₸, февральские не изменились |

| КП-9 | Клиент передаёт `cardToken` чужой карты | `GET /alerts/settings` | 404 «Карта не найдена» |

### Откат
Функция включается флагом `alerts.monthlyLimit.enabled`. При откате флаг выключается: экран «Уведомления» скрывается,
push не отправляются, учёт расходов и сохранённые настройки не удаляются.

## Часть B. REST API

Дочерний документ части A: «Уведомление о расходах по карте — REST API».

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Controller** | AlertsController |
| **Authorization** | Bearer-токен сессии мобильного банка; доступ только к картам владельца сессии |
| **Base URL** | Dev: `https://dev-api.bank.example/alerts`. Prod: `https://api.bank.example/alerts` |
| **Swagger** | `https://dev-api.bank.example/swagger/alerts` |
| **Формат** | `application/json`, кодировка UTF-8 |

### Метод 1. Чтение настроек — `GET /alerts/settings`

**Query-параметры**

| Parameter | Format | Mandatory | Logic | Description |
| :--- | :--- | :--- | :--- | :--- |
| `cardToken` | string, 1–64 | Да | Токен карты владельца | Идентификатор карты |

**Ответ 200**

| Parameter | Format | Description |
| :--- | :--- | :--- |
| `limitKzt` | integer или null | Порог в тенге; null, если не задан |
| `enabled` | boolean | Уведомление включено |
| `monthSpentKzt` | integer | Расходы текущего месяца в тенге, округление вниз |
| `month` | string | Текущий месяц, ГГГГ-ММ |

```json
{"limitKzt":50000,"enabled":true,"monthSpentKzt":12000,"month":"2026-11"}
```

### Метод 2. Сохранение настроек — `PUT /alerts/settings`

**Тело запроса**

| Parameter | Format | Mandatory | Logic | Description |
| :--- | :--- | :--- | :--- | :--- |
| `cardToken` | string, 1–64 | Да | Токен карты владельца | Идентификатор карты |
| `limitKzt` | integer | Да, если `enabled` = true | 1 000–1 000 000 включительно | Порог в тенге |
| `enabled` | boolean | Да | true или false | Уведомление включено |

```json
{"cardToken":"tok_42","limitKzt":50000,"enabled":true}
```

**Логика**
1. Проверить сессию; без сессии — 401.
2. Проверить, что карта принадлежит владельцу сессии; иначе — 404.
3. Проверить параметры; при ошибке — 400, сохранённая настройка не меняется.
4. Заменить настройку целиком и вернуть 200 с сохранёнными значениями. Повторный запрос с теми же значениями даёт тот же результат.

**Ответ 200** — тело как у метода 1 без полей `monthSpentKzt` и `month`.

### Коды ответов (оба метода)

| Код | Когда | Тело |
| :--- | :--- | :--- |
| 200 | Успешно | см. описание метода |
| 400 | Параметры отсутствуют или вне допустимых значений | `{"code":"LIMIT_OUT_OF_RANGE","message":"Порог — целое число от 1 000 до 1 000 000 ₸"}` или `{"code":"BAD_REQUEST","message":"Некорректный запрос"}` |
| 401 | Нет действующей сессии | `{"code":"UNAUTHORIZED","message":"Требуется вход"}` |
| 404 | Карта не найдена или принадлежит другому клиенту | `{"code":"CARD_NOT_FOUND","message":"Карта не найдена"}` |
| 500 | Внутренняя ошибка; настройка не изменена | `{"code":"INTERNAL","message":"Ошибка сервиса, повторите позже"}` |
