### Глоссарий

| Термин | Определение |
| :--- | :--- |
| Порог | Сумма в тенге, заданная клиентом для карты. В документе это понятие называется только так; в API и данных ему соответствуют поля `limitKzt` и `limit_kzt`. |
| Подходящая карта | Карта клиента в статусе «активна» с валютой счёта KZT. |
| Покупка | Операция с категорией `PURCHASE_POS` (оплата в торговой точке) или `PURCHASE_ECOM` (оплата в интернете). |
| Проведённая покупка | Покупка, по которой процессинг передал событие `POSTED` (клиринг выполнен). Авторизация без клиринга не учитывается. |
| Дата совершения | Дата и время авторизации покупки, передаются процессингом в поле `transactionDateTime` по времени Asia/Almaty (UTC+5). |
| Календарный месяц | Период с 00:00:00 первого числа до 23:59:59 последнего числа месяца по времени Asia/Almaty (UTC+5). |
| Текущий месяц | Календарный месяц, в котором сервис расходов обрабатывает событие. |
| Расходы месяца | Сумма проведённых покупок с датой совершения в этом месяце за вычетом примененных к ним возвратов, в тиынах. |
| Сервис расходов | Компонент, который учитывает расходы месяца и решает, отправлять ли push. |
| Сервис push | Компонент, который доставляет push на устройства клиента через внешние сервисы уведомлений. |

### Цели
Клиент получает push в тот момент, когда его расходы за месяц достигают заданного порога. Скорость передачи push задана
требованием НФТ-1. Время доставки на устройство после передачи в сервис push зависит от внешних сервисов уведомлений
и в этом документе не нормируется.

### Архитектура решения
Мобильное приложение → AlertsController → хранилище настроек. Карточный процессинг → сервис расходов → сервис push.
Сервис расходов читает настройки карты из хранилища настроек.

### Дизайн процесса UI
Путь: Карты → карта → Расходы → Уведомления. Экран доступен только для подходящей карты; для остальных карт пункт
«Уведомления» не показывается. При открытии экран вызывает `GET /settings` (часть B) и показывает: переключатель
«Уведомлять о пороге», поле «Порог, ₸», строку «Расходы за {месяц год}: {сумма} ₸» (например, «Расходы за ноябрь 2026:
12 000 ₸») и кнопку «Сохранить». Кнопка вызывает `PUT /settings`.

| Ситуация | Что видит клиент |
| :--- | :--- |
| `GET /settings` вернул 401, 404, 422 или 500 | Экран ошибки «Не удалось загрузить настройки, повторите позже» |
| `PUT /settings` вернул 400 | Текст из поля `message` ответа под полем «Порог, ₸»; введённые значения остаются на экране |
| `PUT /settings` вернул 401, 404, 422 или 500 | Сообщение «Не удалось сохранить настройки, повторите позже»; введённые значения остаются на экране |

### Требования к изменениям

#### BPMN схема процесса
1. Процессинг передаёт событие `POSTED` или `REFUND`.
2. Сервис расходов пропускает событие, если событие с тем же `operationId` уже обработано (И-2).
3. Сервис расходов учитывает событие в расходах месяца по дате совершения (Ф-2, Ф-3).
4. Сервис расходов проверяет условие отправки push (Ф-4) и при его выполнении передаёт push в сервис push.
5. Завершение.

#### Функциональные требования
* **Ф-1** (Must). Держатель подходящей карты задаёт порог — целое число тенге от 1 000 до 1 000 000 включительно — и
  включает или выключает уведомление. Для карты без сохранённых настроек уведомление выключено, порог не задан.
* **Ф-2** (Must). В расходы месяца входят только проведённые покупки по подходящей карте, на сумму, списанную со счёта
  карты в тенге, независимо от валюты покупки (поле `amountTiyn`). Операции других категорий (`TRANSFER`,
  `CASH_WITHDRAWAL`, `FEE`, `TOP_UP`) в расходы не входят. Покупка относится к месяцу по дате совершения.
* **Ф-3** (Must). Возврат (событие `REFUND` с `originalOperationId` учтённой покупки) уменьшает расходы того месяца,
  к которому относится исходная покупка, на сумму возврата. Возврат по операции, не вошедшей в расходы, не учитывается.
  Возврат не отменяет уже отправленный push и сам push не вызывает.
* **Ф-4** (Must). После учёта проведённой покупки push отправляется, если выполнены все условия: уведомление включено,
  порог задан, покупка относится к текущему месяцу, расходы месяца не ниже порога (`spent_tiyn` ≥ `limit_kzt` × 100) и
  push за этот месяц по карте ещё не отправлен (`push_sent_at` пусто). Других случаев отправки push нет. По карте
  отправляется не больше одного push за календарный месяц.
* **Ф-5** (Must). Изменение порога или переключателя не меняет расходы месяца и само по себе push не вызывает; новые
  значения применяются при обработке следующей проведённой покупки по правилу Ф-4.
* **Ф-6** (Must). Расходы месяца учитываются и при выключенном уведомлении.
* **Ф-7** (Should). Покупка, проведённая после окончания месяца, в котором она совершена, увеличивает расходы этого
  прошлого месяца; push за прошлый месяц не отправляется, так как покупка не относится к текущему месяцу (Ф-4).

### Sequence Diagram
1. Процессинг → сервис расходов: событие с полями `operationId`, `eventType` (`POSTED` / `REFUND`), `category`
   (`PURCHASE_POS`, `PURCHASE_ECOM`, `TRANSFER`, `CASH_WITHDRAWAL`, `FEE`, `TOP_UP`), `cardToken`, `panLast4`,
   `amountTiyn` (сумма списания в тенге, в тиынах), `transactionDateTime`; для возврата — `originalOperationId`.
2. Сервис расходов → хранилище настроек: получить `limit_kzt` и `enabled` карты.
3. Сервис расходов → сервис push: ключ идемпотентности `{cardToken}:{ГГГГ-ММ}`, `cardToken`, `panLast4`, `limitKzt`,
   расходы месяца в тенге с округлением вниз, месяц. Текст push: «Расходы по карте •• {panLast4} за {месяц год}
   достигли {расходы} ₸ при пороге {порог} ₸».
4. Сервис push → сервис расходов: подтверждение приёма в течение 10 секунд; после подтверждения сервис расходов
   записывает `push_sent_at`. Сервис push не доставляет повторно сообщение с уже принятым ключом идемпотентности.

### Нефункциональные требования
* **НФТ-1** (Must). Push передаётся в сервис push не позднее 60 секунд после получения сервисом расходов события
  `POSTED`, на котором выполнилось условие Ф-4, для 95% таких событий за сутки и не позднее 120 секунд — для 99%.
  Измеряется по журналу сервиса расходов.
* **НФТ-2** (Must). Сервис расходов обрабатывает поток 300 событий в секунду в течение 15 минут без нарушения НФТ-1;
  проверяется нагрузочным тестом.
* **НФТ-3** (Must). Доступность методов части B — 99,5% минут в календарный месяц. Минута считается недоступной, если
  синтетический запрос мониторинга к `GET /settings` получил ответ 5xx или не получил ответ за 2 секунды.
* **НФТ-4** (Must). Если сервис push не подтвердил приём за 10 секунд, сервис расходов делает ещё 3 повторные попытки с
  интервалом 60 секунд (всего 4 попытки) с тем же ключом идемпотентности. Если все 4 попытки неуспешны, `push_sent_at`
  остаётся пустым, событие записывается в журнал ошибок; следующая проведённая покупка этого месяца снова проверяется по Ф-4.
* **НФТ-5** (Must). Метрики: задержка от получения события до передачи push, доля неуспешных попыток передачи в сервис
  push, число пропущенных повторных событий. Если доля неуспешных попыток передачи (неуспешные попытки / все попытки)
  за 5 минут превышает 1%, мониторинг создаёт оповещение в канале дежурной смены.

### Требования к данным
* **Д-1** (Must). Настройки карты: `card_token` (токен карты, не номер карты), `pan_last4` (последние 4 цифры номера),
  `limit_kzt` (целое, тенге, может быть пустым — порог не задан), `enabled` (логический, по умолчанию false),
  `updated_at` (время Asia/Almaty).
* **Д-2** (Must). Расходы месяца: `card_token`, `month` (ГГГГ-ММ по дате совершения), `spent_tiyn` (целое, тиыны, не
  меньше 0), `push_sent_at` (время записи подтверждения push; пусто, если push не отправлен).
* **Д-3** (Must). Обработанные события: `operation_id` (уникальный), `card_token`, `event_type`, `category`,
  `amount_tiyn`, `transaction_datetime`, `original_operation_id` для возврата, `received_at`.
* **Д-4** (Must). Сравнение с порогом выполняется в тиынах: `spent_tiyn` ≥ `limit_kzt` × 100.
* **Д-5** (Should). Записи Д-2 и Д-3 удаляются через 13 месяцев после окончания месяца, к которому относятся. Записи Д-1
  удаляются через 30 дней после закрытия карты.

### Требования к интеграции
* **И-1** (Must). Приложение читает и сохраняет настройки методами части B.
* **И-2** (Must). Событие с уже обработанным `operationId` пропускается: оно не меняет расходы месяца и не вызывает push.
* **И-3** (Must). Если возврат получен раньше исходной покупки, сервис расходов хранит его 30 дней с момента получения
  (`received_at`). Когда исходная покупка приходит в этот срок, сервис расходов сначала учитывает покупку и применённый
  к ней возврат, затем проверяет условие Ф-4 по итоговым расходам. Если покупка не пришла за 30 дней, возврат
  не применяется и записывается в журнал ошибок.
* **И-4** (Must). События по карте, которая не является подходящей, пропускаются и не учитываются.

### Требования к безопасности
* **ИБ-1** (Must). В API, событиях и журналах используется токен карты; полный номер карты не передаётся и не записывается.
* **ИБ-2** (Must). Push и экран приложения показывают только последние четыре цифры номера карты.
* **ИБ-3** (Must). Методы части B доступны только владельцу карты по сессии мобильного банка; для чужой и для
  несуществующей карты возвращается 404, чтобы не раскрывать существование карты.

### Требования к тестированию

#### Тестирование требований
Ответственный — тестировщик команды карт. Функциональные требования, И-2, И-3, НФТ-4 и ИБ-1 – ИБ-3 проверяются
критериями приёмки ниже (столбец «Требование»). НФТ-1, НФТ-3 и НФТ-5 проверяются по метрикам мониторинга на
тестовом стенде, НФТ-2 — нагрузочным тестом.

### Откат
Функция включается флагом `alerts.monthlyLimit.enabled`. При выключенном флаге экран «Уведомления» скрыт, push не
отправляются, а события продолжают учитываться в расходах месяца; сохранённые настройки не удаляются. После повторного
включения флага push отправляются по правилу Ф-4 при следующей проведённой покупке.

## Часть B. REST API

Дочерний документ части A: «Уведомление о расходах по карте — REST API».

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Controller** | AlertsController |
| **Authorization** | Bearer-токен сессии мобильного банка; доступ только к картам владельца сессии |
| **Base URL** | Dev: `https://dev-api.bank.example/alerts`. Prod: `https://api.bank.example/alerts`. Пути методов ниже указаны относительно Base URL |
| **Swagger** | `https://dev-api.bank.example/swagger/alerts` |

### Метод 1. Чтение настроек — `GET /settings`

**Query-параметры**

| Parameter | Format | Mandatory | Logic | Description |
| :--- | :--- | :--- | :--- | :--- |
| `cardToken` | string, 1–64 | Да | Токен карты владельца | Идентификатор карты |

**Ответ 200**

| Parameter | Format | Description |


### Метод 2. Сохранение настроек — `PUT /settings`

**Тело запроса**

| Parameter | Format | Mandatory | Logic | Description |
| :--- | :--- | :--- | :--- | :--- |
| `cardToken` | string, 1–64 | Да | Токен карты владельца | Идентификатор карты |
| `enabled` | boolean | Да | true или false | Уведомление включено |
| `limitKzt` | integer | Да, если `enabled` = true; иначе необязателен | 1 000–1 000 000 включительно | Порог в тенге |

```json
{"cardToken":"tok_42","limitKzt":50000,"enabled":true}
```

**Логика**
1. Проверить сессию; без сессии — 401.
2. Проверить, что карта принадлежит владельцу сессии; иначе — 404.
3. Проверить, что карта подходящая (активна, валюта KZT); иначе — 422.
4. Проверить параметры; при ошибке — 400, сохранённые значения не меняются.
5. Сохранить `enabled`. Если `limitKzt` передан, сохранить его; если не передан (допустимо только при `enabled` = false),
   сохранённый порог не меняется.
6. Вернуть 200 с сохранёнными значениями. Повторный запрос с теми же значениями даёт тот же результат.

**Ответ 200** — поля `limitKzt` и `enabled`, как у метода 1.

### Коды ответов (оба метода)

| Код | Когда | Тело |
| :--- | :--- | :--- |
| 200 | Успешно | см. описание метода |
| 400 | `limitKzt` не целое число или вне 1 000–1 000 000, либо отсутствует при `enabled` = true | `{"code":"LIMIT_OUT_OF_RANGE","message":"Порог — целое число от 1 000 до 1 000 000 ₸"}` |
| 400 | Отсутствует или имеет неверный тип любой другой параметр | `{"code":"BAD_REQUEST","message":"Некорректный запрос"}` |

| 500 | Внутренняя ошибка; сохранённые значения не изменены | `{"code":"INTERNAL","message":"Ошибка сервиса, повторите позже"}` |
