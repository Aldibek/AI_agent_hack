**Что исправить в первую очередь:**

1. 🔴 **F-03 · Ошибочная сумма: 200 с ERROR или 400** (строки 149, 204, 215)
   > «При отклонении суммы вернуть прежнее состояние и результат ERROR.»
   Сценарий: запрос с amount=999 или amount=1000001. Разработчик А: возвращает HTTP 200 с телом {"result":"ERROR"}. Разработчик Б: возвращает HTTP 400 с телом {"message":"Некорректный запрос"}.
   **Исправить:** Разграничить случаи: какие ошибки суммы возвращают 200/ERROR, а какие 400 (например, нецелое значение или отсутствие параметра).

2. 🔴 **F-01 · Месяц покупки: дата совершения или дата проведения** (строки 43, 79)
   > «Месяц определяется по дате совершения покупки в Алматы.»
   Сценарий: покупку на 4 000 ₸ совершили 31.01 в 23:58, провели 01.02 в 00:03 по Алматы. Разработчик А: по Ф-2 добавляет 4 000 ₸ к январю, и тест стр. 79 падает. Разработчик Б: по критерию добавляет 4 000 ₸ к февралю и нарушает Ф-2.
   **Исправить:** Закрепить одно правило — по дате совершения или по дате проведения по времени Алматы — и согласовать с ним Ф-2 и критерий стр. 79.

3. 🔴 **F-02 · Второй push после смены порога в том же месяце** (строки 45, 47)
   > «На карту приходится максимум один такой push за календарный месяц.»
   Сценарий: 10 марта расходы достигли порога 50 000 ₸, push отправлен; 12 марта порог изменён на 80 000 ₸; 20 марта расходы стали 81 000 ₸. Разработчик А: по Ф-3 не отправляет push. Разработчик Б: по Ф-4 отправляет второй push за март.
   **Исправить:** Явно указать, сбрасывает ли изменение порога месячный лимит в один push, и привести Ф-3 и Ф-4 к одному правилу.

4. 🔴 **F-04 · Content-Type JSON при отсутствии тела запроса** (строки 184, 186)
   > «- **Content-Type:** `application/json` .»
   **Исправить:** Убрать Content-Type для запроса либо описать тело.

5. 🔴 **F-05 · Заголовок «200 Created» смешивает коды 200 и 201** (строки 190, 206)
   > «Если результат 200 или 201 — успешный.»
   Сценарий: клиент впервые сохраняет порог, затем сохраняет его повторно. Разработчик А: отвечает 201, затем 200. Разработчик Б: оба раза отвечает 200.
   **Исправить:** Указать единственный код успешного сохранения.

**Главные вопросы автору:**

- По какой дате покупка относится к месяцу? (Дата совершения покупки по Алматы / Дата проведения по Алматы) → F-01
- Сбрасывает ли смена порога лимит в один push в месяц? (Да, после смены порога разрешён новый push / Нет, в месяце всегда не больше одного push) → F-02
- Откуда приложение получает текущий порог и сумму за месяц? (Отдельный GET-метод чтения / Расширенный ответ существующего метода) → F-08

## Приложение. Методика

1. Текст документа извлекается кодом с сохранением номеров строк (и страниц PDF).
2. Нарезка на требования — детерминированно по разделам шаблона (ФТ, НФТ, данные, интеграция, критерии приёмки, API).
3. Детерминированные правила: заглушки шаблона, размытые слова (29148 §5.2.7), семантика HTTP, коды ответов, единицы, часовой пояс, границы диапазонов и их покрытие критериями приёмки, арифметика критериев приёмки, ссылки на документы.
4. Три независимых прохода LLM параллельно, у каждого своя задача: (1) каждое требование по отдельности и его статус; (2) разбор глазами пяти ролей — разработчик, тестировщик, архитектор/ИБ, бизнес-аналитик, злонамеренный подрядчик; (3) «два разработчика» — две добросовестные реализации одного правила и сценарий, где они расходятся. Параллельно отдельный вызов строит матрицу покрытия требований критериями приёмки.
5. Проверка цитат кодом: находка без дословной цитаты из документа удаляется.
6. Склейка одинаковых находок кодом; затем один вызов-критик пытается опровергнуть каждую находку по тексту документа, склеивает оставшиеся дубли и расставляет приоритет вопросов. Тексты находок остаются авторскими (от ревьюеров).
7. Вердикт — по правилу: есть блокер в ключевых разделах → начинать нельзя; есть существенные → с оговорками.

**Шкалы:** тяжесть — 🔴 блокер (нельзя начинать разработку/тест), 🟠 существенный, 🟡 незначительный; доказанность — [Д] доказано текстом, [У] вопрос к автору, [Ш] шаблон/оформление.
