**Что исправить в первую очередь:**

1. 🔴 **F-03 · Неверная сумма: 200 с result=ERROR или статус 400** (строки 149, 190, 204, 215)
   > «При отклонении суммы вернуть прежнее состояние и результат ERROR.»
   Сценарий: запрос saveLimit с cardId=demo-42, amount=999, enabled=1. Разработчик А: возвращает 200 {"result":"ERROR","message":"Проверьте сумму"}. Разработчик Б: возвращает 400 {"message":"Некорректный запрос"}.
   **Исправить:** Разграничить случаи 400 и 200/ERROR перечнем: сумма вне диапазона, нецелая сумма, enabled не 0/1, отсутствующий параметр.

2. 🔴 **F-07 · Нет метода чтения настроек и суммы за месяц** (строки 31, 66, 124)
   > «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API».»
   Сценарий: клиент открывает экран «Уведомления» с ранее сохранённым порогом 50 000 ₸ и расходами 30 000 ₸. Разработчик А: вызывает saveLimit как чтение и рискует перезаписать настройку. Разработчик Б: заводит собственный метод чтения вне спецификации.
   **Исправить:** Добавить в часть B метод чтения порога, признака включения и суммы за текущий месяц; в описании saveLimit оставить только сохранение.

3. 🔴 **F-06 · Раздел «403 Forbidden» описывает ответ 404** (строки 218, 233, 235)
   > «403. Unsuccessful — Forbidden»
   Сценарий: владелец карты demo-42 вызывает saveLimit с cardId другого клиента. Разработчик А: возвращает 403. Разработчик Б: возвращает 404 {"message":"Карта не найдена"}.
   **Исправить:** Переименовать раздел в «404. Not Found», добавить 404 в перечень статусов и определить, возвращается ли 403 вообще и в каком случае.

4. 🔴 **F-01 · Месяц покупки: Ф-2 и критерий приёмки дают разный ответ** (строки 43, 79)
   > «Месяц определяется по дате совершения покупки в Алматы.»
   Сценарий: покупка совершена 31.01 в 23:58 на 4 000 ₸, проведена 01.02 в 00:03 по Алматы. Разработчик А: по Ф-2 добавляет 4 000 ₸ к январю, и тест строки 79 падает. Разработчик Б: по критерию добавляет 4 000 ₸ к февралю, и нарушается Ф-2.
   **Исправить:** Закрепить, какая дата определяет месяц (совершения или проведения), и привести критерий в соответствие с правилом, указав часовой пояс обоих времён.

5. 🔴 **F-02 · Лимит одного push в месяц противоречит повторному push после смены порога** (строки 45, 47)
   > «На карту приходится максимум один такой push за календарный месяц.»
   Сценарий: 10.03 расходы достигли порога 50 000 ₸ и push отправлен; 12.03 порог изменён на 80 000 ₸ при расходах 52 000 ₸; 15.03 покупка доводит расходы до 81 000 ₸. Разработчик А: по Ф-3 не отправляет второй push. Разработчик Б: по Ф-4 отправляет второй push.
   **Исправить:** Явно указать, сбрасывает ли изменение порога месячный лимит push, и сформулировать Ф-3 с этим исключением или без него.

**Главные вопросы автору:**

- По какой дате относить покупку к месяцу? (По дате совершения по Алматы / По дате проведения по Алматы) → F-01
- Каким способом приложение получает текущие настройки и сумму за месяц? (отдельный метод чтения / расширить ответ существующего метода) → F-07
- Сбрасывает ли изменение порога лимит «один push в месяц»? (да, после смены порога разрешён новый push / нет, в месяце не более одного push при любых изменениях) → F-02

## Приложение. Методика

1. Текст документа извлекается кодом с сохранением номеров строк (и страниц PDF).
2. Нарезка на требования — детерминированно по разделам шаблона (ФТ, НФТ, данные, интеграция, критерии приёмки, API).
3. Детерминированные правила: заглушки шаблона, размытые слова (29148 §5.2.7), семантика HTTP, коды ответов, единицы, часовой пояс, границы диапазонов и их покрытие критериями приёмки, арифметика критериев приёмки, ссылки на документы.
4. Три независимых прохода LLM параллельно, у каждого своя задача: (1) каждое требование по отдельности и его статус; (2) разбор глазами пяти ролей — разработчик, тестировщик, архитектор/ИБ, бизнес-аналитик, злонамеренный подрядчик; (3) «два разработчика» — две добросовестные реализации одного правила и сценарий, где они расходятся. Параллельно отдельный вызов строит матрицу покрытия требований критериями приёмки.
5. Проверка цитат кодом: находка без дословной цитаты из документа удаляется.
6. Склейка одинаковых находок кодом; затем один вызов-критик пытается опровергнуть каждую находку по тексту документа, склеивает оставшиеся дубли и расставляет приоритет вопросов. Тексты находок остаются авторскими (от ревьюеров).
7. Вердикт — по правилу: есть блокер в ключевых разделах → начинать нельзя; есть существенные → с оговорками.

**Шкалы:** тяжесть — 🔴 блокер (нельзя начинать разработку/тест), 🟠 существенный, 🟡 незначительный; доказанность — [Д] доказано текстом, [У] вопрос к автору, [Ш] шаблон/оформление.

**Характеристики отдельного требования:** Необходимость — требование нужно; без него система не выполнит цель; Уместность — уровень детализации соответствует сущности; нет лишних проектных решений; Однозначность — допускает только одно толкование; Полнота — описаны все условия, входы, выходы и ответы на все случаи; Единичность — одно требование — одна возможность/характеристика; Выполнимость — реализуемо в заданных ограничениях; Проверяемость — можно доказать выполнение конечной проверкой (тестом, осмотром); Корректность — точно описывает потребность; нет фактических ошибок; Соответствие шаблону — оформлено по принятому шаблону и стилю.
