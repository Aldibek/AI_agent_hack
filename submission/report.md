## Коротко

**Разработку начинать: нельзя. Тестирование начинать: нельзя.**

**Что исправить в первую очередь:**

1. 🔴 **F-04 · Неясно, успех — это 200 или 201 Created** (строки 151, 165)
   > «Если результат 200 или 201 — успешный.»
   Сценарий: первое сохранение amount=50000, enabled=1 для карты без настройки. Разработчик А: отвечает 200. Разработчик Б: отвечает 201.
   **Исправить:** Указать единственный успешный код и его название.

2. 🔴 **F-02 · Неверная сумма: 200 с ERROR или 400** (строки 121, 163, 171)
   > «При отклонении суммы вернуть прежнее состояние и результат ERROR.»
   Сценарий: запрос с amount=999, enabled=1. Разработчик А: отвечает 200 и {"result":"ERROR","message":"Проверьте сумму"}. Разработчик Б: отвечает 400 и {"message":"Некорректный запрос"}.
   **Исправить:** Закрепить для каждого вида ошибки (сумма вне диапазона, нецелое число, enabled не 0/1, отсутствующий параметр) один статус и одно тело ответа.

3. 🔴 **F-05 · Нет метода чтения настроек и суммы за месяц** (строки 29, 52, 103)
   > «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API».»
   Сценарий: клиент открывает экран «Уведомления» при пороге 50 000 ₸ и расходах 30 000 ₸. Разработчик А: вызывает saveLimit без параметров как чтение. Разработчик Б: придумывает собственный эндпоинт. Ни одна из реализаций не опирается на документ.
   **Исправить:** Добавить в часть B метод чтения, который возвращает порог, признак включения и сумму расходов за текущий месяц, и исправить Description метода сохранения.

4. 🔴 **F-01 · Месяц по дате совершения покупки противоречит критерию приёмки** (строки 38, 64)
   > «Месяц определяется по дате совершения покупки в Алматы.»
   Сценарий: покупка на 4 000 ₸ совершена 31 января в 23:58, проведена 1 февраля в 00:03 по Алматы. Разработчик А: по Ф-2 увеличивает январский счётчик. Разработчик Б: по критерию приёмки увеличивает февральский счётчик.
   **Исправить:** Выбрать одно правило — дата совершения или дата проведения — и привести к нему Ф-2 и критерий приёмки; заодно указать часовой пояс времени 23:58.

5. 🔴 **F-03 · Content-Type JSON при неиспользуемом теле** (строки 147, 148)
   > «* **Content-Type:** `application/json` .»
   **Исправить:** Убрать Content-Type или перенести параметры в JSON-тело.

**Главные вопросы автору:**

- По какой дате относить покупку к месяцу? (По дате совершения покупки (Алматы) / По дате проведения (Алматы)) → F-01
- Чтение реализуется отдельным методом или тем же контроллером? (Отдельный GET-метод чтения / Расширить ответ существующего метода) → F-05
- Сбрасывает ли изменение порога месячный лимит в один push? (Да, после смены порога разрешён ещё один push / Нет, в месяце не больше одного push независимо от смены порога) → F-07

## Приложение. Методика

1. Текст документа извлекается кодом с сохранением номеров строк (и страниц PDF).
2. Нарезка на требования — детерминированно по разделам шаблона (ФТ, НФТ, данные, интеграция, критерии приёмки, API).
3. Детерминированные правила: заглушки шаблона, размытые слова (29148 §5.2.7), семантика HTTP, коды ответов, единицы, часовой пояс, границы диапазонов и их покрытие критериями приёмки, арифметика критериев приёмки, ссылки на документы.
4. Три независимых прохода LLM параллельно, у каждого своя задача: (1) каждое требование по отдельности и его статус; (2) разбор глазами пяти ролей — разработчик, тестировщик, архитектор/ИБ, бизнес-аналитик, злонамеренный подрядчик; (3) «два разработчика» — две добросовестные реализации одного правила и сценарий, где они расходятся. Параллельно отдельный вызов строит матрицу покрытия требований критериями приёмки.
5. Проверка цитат кодом: находка без дословной цитаты из документа удаляется.
6. Склейка одинаковых находок кодом; затем один вызов-критик пытается опровергнуть каждую находку по тексту документа, склеивает оставшиеся дубли и расставляет приоритет вопросов. Тексты находок остаются авторскими (от ревьюеров).
7. Вердикт — по правилу: есть блокер в ключевых разделах → начинать нельзя; есть существенные → с оговорками.

**Шкалы:** тяжесть — 🔴 блокер (нельзя начинать разработку/тест), 🟠 существенный, 🟡 незначительный; доказанность — [Д] доказано текстом, [У] вопрос к автору, [Ш] шаблон/оформление.

**Характеристики отдельного требования:** Необходимость — требование нужно; без него система не выполнит цель; Уместность — уровень детализации соответствует сущности; нет лишних проектных решений; Однозначность — допускает только одно толкование; Полнота — описаны все условия, входы, выходы и ответы на все случаи; Единичность — одно требование — одна возможность/характеристика; Выполнимость — реализуемо в заданных ограничениях; Проверяемость — можно доказать выполнение конечной проверкой (тестом, осмотром); Корректность — точно описывает потребность; нет фактических ошибок; Соответствие шаблону — оформлено по принятому шаблону и стилю.
