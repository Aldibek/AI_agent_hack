## Коротко

**Разработку начинать: нельзя. Тестирование начинать: нельзя.**

- Требований: **53** — с дефектами 33, проверено без дефектов 20.
- Замечаний: **34** — 🔴 блокеров 2, 🟠 существенных 13, 🟡 незначительных 19.

**Что исправить в первую очередь:**

1. 🔴 **F-01 · Месяц поздно проведённой покупки: дата покупки или дата проведения** (строки 38, 64)
   > «Месяц определяется по дате совершения покупки в Алматы.»
   Сценарий: покупка 31 января в 23:58 на 4 000 ₸ проведена 1 февраля в 00:03 по Алматы. Разработчик А: добавляет 4 000 ₸ в январь по Ф-2. Разработчик Б: добавляет 4 000 ₸ в февраль по критерию приёмки.
   **Исправить:** Согласовать Ф-2 и критерий приёмки: закрепить одну дату (совершения или проведения) и указать часовой пояс обеих отметок времени.

2. 🔴 **F-02 · Нет метода чтения настроек и суммы за месяц** (строки 29, 52, 103)
   > «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API».»
   Сценарий: клиент открывает экран «Уведомления» для карты с сохранённым порогом 50 000 ₸ и расходами 12 000 ₸. Разработчик А: вызывает saveLimit как чтение, но метод требует amount и перезаписывает настройку. Разработчик Б: показывает пустые поля, потому что метода чтения нет.
   **Исправить:** Добавить отдельный метод чтения настроек и суммы расходов за текущий месяц и исправить Description у saveLimit.

3. 🟠 **F-04 · Неверная сумма: 400 Bad request или 200 с result=ERROR** (строки 121, 163, 165, 171)
   > «При отклонении суммы вернуть прежнее состояние и результат ERROR.»
   Сценарий: запрос amount=999, enabled=1. Разработчик А: возвращает 400 {"message":"Некорректный запрос"}. Разработчик Б: возвращает 200 {"result":"ERROR","message":"Проверьте сумму"}.
   **Исправить:** Закрепить один код и одно тело ответа для ошибок валидации amount и enabled.

4. 🟠 **F-06 · Метод GET используется для изменения состояния** (строки 103, 104, 108, 109)
   > «REST type \| GET»
   Повтор или предзагрузка GET-запроса промежуточным узлом повторно сохраняет настройку. Идентификатор карты и порог попадают в журналы URL.
   **Исправить:** Для сохранения использовать POST/PUT с параметрами в теле запроса; GET оставить для чтения настройки.

5. 🟠 **F-05 · Чужая карта: 403 Forbidden или 404** (строки 175, 188, 189)
   > «**403.** Ответ в случае, если на указанный ресурс доступ запрещен.»
   Сценарий: клиент с валидной сессией шлёт cardId карты другого клиента. Разработчик А: возвращает 403. Разработчик Б: возвращает 404 {"message":"Карта не найдена"}.
   **Исправить:** Оставить один код для чужой карты и указать, в каких случаях вообще возвращается 403.

**Главные вопросы автору:**

- По какой дате относить покупку к месяцу? (По дате совершения покупки / По дате проведения) → F-01
- Как приложение получает текущие настройки и сумму за месяц? (Отдельный GET-метод чтения / saveLimit без параметров возвращает текущее состояние) → F-02
- Отправлять ли push при достижении нового порога, если в этом месяце push уже был? (Да, смена порога сбрасывает лимит / Нет, максимум один push в месяц всегда) → F-03

7. Вердикт — по правилу: есть блокер в ключевых разделах → начинать нельзя; есть существенные → с оговорками.

**Шкалы:** тяжесть — 🔴 блокер (нельзя начинать разработку/тест), 🟠 существенный, 🟡 незначительный; доказанность — [Д] доказано текстом, [У] вопрос к автору, [Ш] шаблон/оформление.

**Характеристики отдельного требования:** Необходимость — требование нужно; без него система не выполнит цель; Уместность — уровень детализации соответствует сущности; нет лишних проектных решений; Однозначность — допускает только одно толкование; Полнота — описаны все условия, входы, выходы и ответы на все случаи; Единичность — одно требование — одна возможность/характеристика; Выполнимость — реализуемо в заданных ограничениях; Проверяемость — можно доказать выполнение конечной проверкой (тестом, осмотром); Корректность — точно описывает потребность; нет фактических ошибок; Соответствие шаблону — оформлено по принятому шаблону и стилю.
