**Что исправить в первую очередь:**

1. 🔴 **F-03 · Неверная сумма: 200 с ERROR или 400** (строки 145, 149, 204, 215)
   > «При отклонении суммы вернуть прежнее состояние и результат ERROR.»
   Сценарий: запрос amount=999&enabled=1. Разработчик А: возвращает 200 и {"result":"ERROR","message":"Проверьте сумму"}. Разработчик Б: возвращает 400 и {"message":"Некорректный запрос"}.
   **Исправить:** Разграничить случаи: какие ошибки валидации дают 200/ERROR, а какие 400, отдельно для amount, enabled и cardId.

2. 🔴 **F-05 · Статус 200 назван Created, 201 не описан** (строки 190, 206)
   > «#### **200. Successful — Created**»
   Сценарий: первое сохранение порога 50 000 ₸ для карты demo-42. Разработчик А: возвращает 201. Разработчик Б: возвращает 200.
   **Исправить:** Указать один код успеха с корректным названием.

3. 🔴 **F-01 · Критерий приёмки относит январскую покупку к февралю** (строки 43, 79)
   > «Месяц определяется по дате совершения покупки в Алматы.»
   Сценарий: покупку на 4 000₸ совершили 31.01 в 23:58, провели 01.02 в 00:03 по Алматы. Разработчик А: по Ф-2 добавляет 4 000₸ к январю, и тест из строки 79 падает. Разработчик Б: по критерию добавляет к февралю и нарушает Ф-2.
   **Исправить:** Определить, какая дата задаёт месяц: совершения или проведения. Привести Ф-2 и критерий к одному правилу и указать часовой пояс для обеих отметок времени.

4. 🔴 **F-02 · Повторный push после смены порога противоречит лимиту «один в месяц»** (строки 45, 47)
   > «На карту приходится максимум один такой push за календарный месяц.»
   Сценарий: 10 марта расходы 50 000 ₸ при пороге 50 000 ₸, push отправлен; 12 марта порог поднят до 60 000 ₸; 20 марта расходы дошли до 60 500 ₸. Разработчик А: отправляет второй push по Ф-4. Разработчик Б: не отправляет, потому что мартовский лимит по Ф-3 исчерпан.
   **Исправить:** Явно указать, сбрасывает ли изменение порога месячный лимит push, и добавить соответствующий критерий приёмки.

5. 🔴 **F-04 · Content-Type JSON задан для запроса без тела** (строки 184, 186)
   > «- **Content-Type:** `application/json` .»
   **Исправить:** Убрать Content-Type для запроса или описать тело.

**Главные вопросы автору:**

- По какой дате определяется месяц учёта покупки? (дата совершения по Алматы / дата проведения по Алматы) → F-01
- Сбрасывает ли изменение порога лимит «один push в месяц»? (Да, после изменения порога разрешён ещё один push в этом месяце / Нет, лимит один push в месяц при любых изменениях) → F-02
- Как приложение получает текущие настройки и сумму за месяц? (Отдельный метод чтения в части B / Сумма за месяц берётся из другого сервиса, который нужно указать) → F-06

## Приложение. Методика

1. Текст документа извлекается кодом с сохранением номеров строк (и страниц PDF).
2. Нарезка на требования — детерминированно по разделам шаблона (ФТ, НФТ, данные, интеграция, критерии приёмки, API).
3. Детерминированные правила: заглушки шаблона, размытые слова (29148 §5.2.7), семантика HTTP, коды ответов, единицы, часовой пояс, границы диапазонов и их покрытие критериями приёмки, арифметика критериев приёмки, ссылки на документы.
4. Три независимых прохода LLM параллельно, у каждого своя задача: (1) каждое требование по отдельности и его статус; (2) разбор глазами пяти ролей — разработчик, тестировщик, архитектор/ИБ, бизнес-аналитик, злонамеренный подрядчик; (3) «два разработчика» — две добросовестные реализации одного правила и сценарий, где они расходятся. Параллельно отдельный вызов строит матрицу покрытия требований критериями приёмки.
5. Проверка цитат кодом: находка без дословной цитаты из документа удаляется.
6. Склейка одинаковых находок кодом; затем один вызов-критик пытается опровергнуть каждую находку по тексту документа, склеивает оставшиеся дубли и расставляет приоритет вопросов. Тексты находок остаются авторскими (от ревьюеров).
7. Вердикт — по правилу: есть блокер в ключевых разделах → начинать нельзя; есть существенные → с оговорками.

**Шкалы:** тяжесть — 🔴 блокер (нельзя начинать разработку/тест), 🟠 существенный, 🟡 незначительный; доказанность — [Д] доказано текстом, [У] вопрос к автору, [Ш] шаблон/оформление.

**Характеристики отдельного требования:** Необходимость — требование нужно; без него система не выполнит цель; Уместность — уровень детализации соответствует сущности; нет лишних проектных решений; Однозначность — допускает только одно толкование; Полнота — описаны все условия, входы, выходы и ответы на все случаи; Единичность — одно требование — одна возможность/характеристика; Выполнимость — реализуемо в заданных ограничениях; Проверяемость — можно доказать выполнение конечной проверкой (тестом, осмотром); Корректность — точно описывает потребность; нет фактических ошибок; Соответствие шаблону — оформлено по принятому шаблону и стилю.
